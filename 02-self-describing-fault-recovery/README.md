## 单进程事件驱动仿真

1 个协调端 + 4 个工作节点，作业 = 12 个分片任务 × 3 个阶段。阶段输出由 numpy **真实计算**，时间为仿真秒（心跳 0.5 s、租约 2 s、状态传输 50 MB/s + 2 ms）。`src/task.py` 的 `TaskDesc` 是自描述任务，`src/fault.py` 定义故障与 `plan_recovery`，`src/des.py` 是协调端/工作节点协议仿真。

```bash
python3 -m src.experiment   # λ 调参 + 实验A（状态保存策略）+ 实验B（故障类型×恢复策略）+ 出图
python3 -m pytest -q
```

- 实验 A：4 种规模组合 × 3 故障阶段 × 3 故障时机 × 5 次重复 × 3 策略。
- 实验 B：致命/瞬态/性能退化 × 无恢复/盲目重试/自描述策略化恢复，各 200 次；另含「盲目重试且关闭去重」消融。
- 输出：`lambda_tuning.csv`、`expA_*.csv`、`expB_*.csv`，`fig1`–`fig8` PNG。

## 多进程原型（对应任务书）

任务书要求 1 个协调端和不少于 3 个工作节点，用多进程或本机通信；并在运行中主动杀掉一个工作进程来注入故障。`src/mp_runtime.py` 就是这套实现，协调进程保持运行：

- 工作节点是独立进程（运行时默认 4 个，至少 3 个），用标准库 `multiprocessing` 队列通信。
- 下发的自描述任务带有 `task_id`、`stage_id`、`input_ref`、所需中间结果 `needed_refs`。
- 协调端保存已确认状态，按 `(task_id, stage_id)` 去重。
- 工作进程在阶段执行期间写心跳。协调端发现进程退出，或心跳超时，就把该任务从未完成阶段重新派发（有检查点则从检查点之后继续，否则从头算）。
- 故障注入是对正在执行目标阶段的工作进程发送 `SIGKILL`，不是把节点标记成“已死”。

状态传输量按记录的逻辑字节计（含填充，与仿真一致）。保存判决使用和仿真相同的 `C_k`、`P_k`，恢复时间用墙钟。范围是单个工作进程崩溃。

```bash
python3 -m src.mp_experiment   # 4 个工作进程、3 个任务；两种规模 × 三种策略 × 4 次；写 CSV 和图
python3 -m pytest -q           # 含杀死工作进程后输出与无故障运行一致，以及去重
```

实验把故障固定在任务 0 的变换阶段，并留一个空闲工作进程接手，用来比较保存策略，而不是比较任务排在队列的哪个位置。

输出：`mp_runs.csv`、`mp_summary.csv`、`mp_fault_free.csv`、`mp_meta.csv`，以及 `fig_mp1`–`fig_mp3`。指标是恢复时间、重复计算、状态传输量、完成率；每次故障运行的最终摘要都与无故障运行比对。
